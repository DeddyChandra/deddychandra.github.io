How a single data-type mismatch cost us 99% of our query performance

This is a placeholder post — replace with your actual writeup. The skeleton below is here to show what a long-form post looks like in this design.

One Tuesday morning, our PagerDuty lit up. A read endpoint that usually returned in under 10 ms was now sitting at 7.9 seconds. The table backing it had grown to a few million rows, but nothing dramatic. So why was Postgres falling over?

The smoking gun in EXPLAIN

The first thing I always do is grab the actual plan, not just EXPLAIN but EXPLAIN (ANALYZE, BUFFERS). Here's the offender:

Parallel Seq Scan on bookings  (cost=0.00..123456.78 rows=2345678)
  Filter: ((user_id)::text = '12345'::text)
  Rows Removed by Filter: 9876543

See it? (user_id)::text. Postgres was casting the column to text on every row, which made my carefully created index on user_id completely useless.

Why that happens

The column was BIGINT, but somewhere in the call chain a string parameter got passed in. Postgres can't use a BIGINT index for a text comparison, so it falls back to a Parallel Seq Scan and crawls the whole table.

The fix

One line in the application code, casting the parameter to a long. The next plan looked like this:

Index Scan using bookings_user_id_idx on bookings  (cost=0.43..8.45 rows=1)
  Index Cond: (user_id = 12345)

Latency dropped from 7,969 ms → 0.057 ms. A 99% reduction, from a one-line patch.

Lessons

  • Always read EXPLAIN ANALYZE — predicates that wrap a column in a function or cast almost never use the index.
  • Stricter ORM/RPC type contracts would have caught this earlier.
  • Add APM-driven alerts on p99, not just averages — the average barely budged because most queries took the fast path.
Performance bugs hide in plain sight. The plan tells you the truth.
